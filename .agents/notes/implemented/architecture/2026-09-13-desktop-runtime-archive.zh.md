# Agent Note: 将 Desktop 运行时作为单个已验证归档分发

Status: implemented

[English](2026-09-13-desktop-runtime-archive.md) | 中文

包归属、共享链接和 profile 事务遵循[内置运行时决策](2026-09-08-desktop-bundled-runtime-and-external-plugins.zh.md)。

## 问题

生产依赖图有 11000 个文件。以散文件资源放在签名包内时，其中每一个都是安装器要写进用户机器的文件、发布差异要搬运的区块，以及任何可承受的启动检查都覆盖不到的条目。包签名在构建时固定了这些字节，之后对磁盘上的依赖树不再作任何保证，因此损坏或篡改既不会被发现，也不会被修复：不可用的模块在加载时才会失败。

这里的安装工作量是产品决策，而不只是体积问题：桌面应用捆绑运行时的根本理由，就是用户安装一次之后，启动时不再执行包安装。

## 决策

`prepare:dsh` 把已准备好的运行时依赖树打包为 `desktop-runtime.tar.zst`，并在旁边写入 `desktop-runtime.tar.zst.sha256`，其中包含归档的 sha256 和条目数。electron-builder 复制这两个文件作为运行时资源；生产依赖树本身不进入应用包。`extraResources` 仍以散文件保留已准备的 Node.js 与 pnpm 运行时，因为 Electron 和展开过程都直接从 `process.resourcesPath` 运行它们。

首次启动用记录的摘要比对归档，把它展开到 `$DSH_HOME/closure/<版本>`，为展开过程中丢失权限位的可执行文件恢复可执行位，并把归档摘要、字节数、条目数和展开树的摘要记入 `.complete`。此后每次启动都对依赖树取摘要并与该记录比对。标记不可读，或文件被修改、缺失、新增时，应用会用已验证字节重新展开；它修复自己的运行时，而不是从不被任何凭证背书的树启动。

`$DSH_HOME/closure/<版本>` 现在是 Host 启动所依据的运行时位置，也是 profile 共享链接解析的目标；`resources/dsh` 不再存在。版本键就是发布版本，因此 Desktop 更新会落到新目录，旧目录被清理。归档展开期间加载页报告确定的进度，其前的摘要计算阶段报告不确定阶段。

## 完整性模型

两个摘要，各自守护对方覆盖不到的部分。

- **归档摘要**是签名包携带的参照。`afterPack` 与 `afterSign` 在应用资源和签名后的应用中再次校验它，因此复制过程丢弃或改动了归档会让构建失败；首次启动在展开任何内容之前再校验一次，不匹配的字节完全拒绝展开——失败信息指向重新安装，而不是启动一个只有部分可信的运行时。
- **树摘要**描述展开结果。按路径排序后对每个文件取哈希，使结果只取决于路径和内容，而不取决于读取顺序，因此展开结果可以与该树写入时记录的摘要比较。这一半负责发现首次启动之后被修改的树，并覆盖归档摘要单独无法覆盖的情况：中断的展开，或之后被就地改动的文件。

展开在 `.tmp-<pid>-<时间>` 同级目录中进行，只有在记录树摘要之后才改名到位，因此中断的尝试不会留下任何后续启动会当作运行时接受的内容。`prepare:dsh` 中的构建期往返校验会把刚写出的归档展开到临时 home，并把该树摘要与打包前的树摘要比较；正是这一步让"产出的归档并非它验证过的树"使打包失败。

逐文件的 `desktop-runtime.json` 描述文件仍留在归档内。它继续记录共享包、发布身份和清单；启动读取它以获取共享包记录和运行时身份，而完整性由上面两个摘要提供。

## 考虑过的替代方案

- **在包内保留散文件依赖树（上游布局）。** 这正是安装器和更新区块为 11000 个文件付出代价的地方，并且让已安装的树处于应用能承受的任何检查之外。它唯一的优势——树内每个文件都被包签名单独封存——通过摘要被签名覆盖的归档而保留下来。
- **把依赖树放进 ASAR。** 后端运行的是上游 Node.js，而不是 Electron 打过补丁的文件系统，所以它无法使用 ASAR 路径，原生模块和派生的可执行文件也需要真实文件。归档展开为普通目录正是为此。
- **每次启动都展开到临时目录。** 这消除了依赖树陈旧的问题，代价是每条启动路径都要解压，包括更新和恢复路径，并且放弃了 profile 链接所解析的、对插件兼容的真实目录。记录树摘要使启动检查保持诚实，而不必支付展开成本。
- **每次启动用描述文件的逐文件清单验证展开树，而不是单个树摘要。** 这是发布验证决策交给打包流程的验证方式；在后端启动前读取 11000 个小文件，成本远高于顺序摘要同样的字节，而且仍然不能让检查具备自愈能力。
- **只信任包签名。** 这样没有任何机制修复损坏或被修改的树，一个被改动的字节就会导致重装。自愈正是让归档（而不是散文件树）随包分发的原因。

## 影响

安装过程写入两个资源，而不是 11000 个文件；首次启动时展开出的树一次性出现在 Harness home 下。用户或进程改动、删除、新增运行时文件后，下次启动会得到一次全新展开，而不是一个诊断结果，因此运行时完整性不会以后端内的加载失败形式出现。

代价落在启动和更新时。归档摘要与树摘要都在后端启动前运行，展开过程会计入首次启动耗时——发布验收会测量它。Desktop 更新也会为新版本重复展开，版本键目录让这一点显式可见，而不是隐藏在安装器里。在参考的 Apple Silicon 构建上，11226 个文件、146 MB 的依赖树对应 29 MB 归档；首次启动约 2.5 秒展开完成，后续启动约 0.4 秒完成树摘要，被损坏的依赖树连同重新展开约 10 秒内恢复。

本 fork 通过修改上游所有的桌面文件来实现归档层：归档模块及其测试是新文件，而 `prepare-dsh.ts`、`electron-builder.config.mjs`、`desktop-build-paths.mjs`、`main.ts`、`paths.ts`、`backend-controller.ts`、启动渲染层和本地化文案属于改动文件。[desktop/README.zh.md](../../../../desktop/README.zh.md)负责上游同步用的补丁清单。

[Desktop README](../../../../apps/desktop/README.zh.md)负责操作说明。[闭包测试](../../../../apps/desktop/tests/runtime-closure.spec.ts)固定两个摘要、可执行位恢复、其他版本的清理，以及文件被修改、缺失、多余或不可读时的行为；[启动测试](../../../../apps/desktop/tests/main-startup.spec.ts)固定展开在 Host 之前运行，以及展开失败时恢复文档留在原处。展开耗时、安装包体积，以及公证后安装包自身的验收仍属于发布环境测量项。
