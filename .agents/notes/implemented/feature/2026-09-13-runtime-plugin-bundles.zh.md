# Agent Note：桌面应用的运行时插件包

Status: implemented

[English](2026-09-13-runtime-plugin-bundles.md) | 中文

## 问题

桌面应用携带的是一个冻结闭包。这正是它能在没有 Node.js、没有包管理器的机器上安装的原因，也正是首个版本直接把「应用内插件安装」列为排除项的原因：要改变应用能做的事，唯一的办法是构建并发布一个新版本。

同类应用都用同一种做法解决同一个问题。VS Code 把 `.vsix` 归档装进 `~/.vscode/extensions`，并在独立的扩展宿主进程里运行，于是「行为不端的扩展无法影响 VS Code」。Claude Desktop 安装 `.mcpb` 包——一个 zip，内含 manifest、服务器代码，以及打包好的 `node_modules`——并以应用自带的运行时把每个包作为子进程运行。Codex 与 ChatGPT 桌面配置的是 MCP server，同样是进程。没有任何一个在应用内跑包管理器，也没有任何一个把插件写进自己已签名的包体内。

而本仓库早已具备这一设计的承重部分，只是没有启用：[`packages/mcp/mcp-client`](../../../../packages/mcp/mcp-client/README.zh.md) 会拉起外部 MCP server、发现其工具、把每个工具注册为 `mcp__<server>__<tool>` 形态的原生工具，并负责断线重连——而没有任何组合包挂载过它。要在运行时安装插件，缺的是一个安放它的存储与一行挂载它的组合项，而不是一套新协议。

## 决策

### 插件是自包含的包，安装在应用之外

存储安装的是 MCP Bundle 格式（`.mcpb`，原 `.dxt`）：一个 zip，内含 `manifest.json`、服务器代码与它的 `node_modules`。采用已发布的格式而非自创格式，意味着作者已经在用的工具链（`mcpb init` / `mcpb pack`）产出的包本应用可直接运行，而为其他宿主构建的包在这里也能被读取。

插件装在 `$DSH_HOME/plugins/<id>/<version>/` 下——既在已签名应用之外，也在更新会替换的路径之外。应用包体不被写入任何东西：闭包保持它的归档、签名与内容。

### 运行时由宿主提供

manifest 里的 `mcp_config.command: "node"` 表达的是一种意图，而不是一条路径。存储把它映射为本应用自己的二进制以 Node 方式重入，并在子进程上设置 `ELECTRON_RUN_AS_NODE=1`——与 shell 启动 harness 用的是同一套机制。因此用户无需安装 Node 就能安装 Node 插件，而这正是 `.mcpb` 包可移植的前提。本宿主无法运行的 `server.type`（`python`、`uv`）在安装时即被拒绝并说明原因，而不是装上去、之后每次启动都失败。

### 一个启用的插件就是一个挂载的 `mcp-client` 实例

`PluginStore` 读取自己的注册表，对每个启用条目，在存储自身的 context 上动态挂载 `@deepseek-ai/dsh-mcp-client`，配置来自 manifest 的 `mcp_config`（先做 `${__dirname}` 与 `${HOME}` 替换）。安装、启用、卸载都在运行中的应用内即时生效：挂载被加上或被销毁，工具随之出现或消失。

### 失败被两重收敛

挂载会把自身的启动失败捕获下来，而不是让 fiber 的激活失败。这是有意的：激活失败会让 cordis 回滚该 fiber，而回滚本身会留下一个无人处理的 rejection——打包宿主的 fail-loud 处理会把它当成进程故障。捕获失败、在注册表视图中报告它、再销毁一个仍处于 ACTIVE 的 fiber，才能把插件故障留在存储内部。

另一半收敛来自架构本身：插件是一个子进程，因此崩溃、卡死或重连预算耗尽，只会带走该插件的工具，别的都不受影响。存储报告状态，宿主照常运行。

### 界面通过存储自己的 loopback 路由访问它

`PluginStore` 通过既有的路由扩展点，在组合自身的 webserver 上注册 `/desktop/plugins`，并拒绝任何非 loopback 的请求。面板是 desktop 子树里的一个浏览器插件，直接抓取这些路由；它需要的文件选择对话框来自 shell 既有的 preload 桥。没有新增特权 RPC 域，因此界面部分没有改动任何上游包。

## 备选方案

**以 patch 层的形式在进程内安装 cordis 插件。** 纸面上这是改动最小的方案——harness 本就组合 patch 层，一个已安装的包贡献一层即可。否决：进程内的插件代码与 harness 共享生命周期与权限，插件崩溃就变成应用崩溃；而且应用需要为任意代码自建一套信任模型，而不是采用同类应用一致使用的进程边界。

**在应用内运行包管理器。** 否决：这是所有同类应用唯一都不做的事。它会把 `pnpm`（约 20MB）塞进产物，让安装依赖应用自己承担的传递依赖解析，而换来的东西自包含包本就提供——`mcpb pack` 与 `vsce package` 的存在正是为了把这份工作交给发布者。

**把闭包解成真实目录，让插件解析变得平常。** 否决：它以改变产物的安装过程（首次启动解压约 355MB）为代价，去解决一个包格式本身并不存在的问题。插件是独立程序，从不需要从 harness 解析任何东西。

**像 Claude Desktop 那样提供策展目录。** 属于推迟而非否决：一旦包格式存在，它就是自然的下一步，而它需要的发布流程不在本次改动范围内。

## 影响

**收益**：无需构建新版本，就能为已安装的应用增加能力；插件的崩溃、卡死或重连耗尽都留在它自己的进程内；插件因位于包体之外而跨应用更新保留；应用自身的安装体验不变，闭包未被触动。

**代价**：插件是独立进程，因此它能贡献的只限于进程边界能承载的东西——目前是它的工具。它无法像进程内插件那样增加界面、prompt 段落或组合行。MCP 的 Resources 与 Prompts 仍未被桥接，此前也是如此。需要交互式配置（`user_config`）的包会被拒绝，而不是装上一份半配置的副本。没有任何东西验证发布者身份：存储检查结构与声明的平台，不检查谁签了这个归档，面板在安装前会说明这一点。

**已知限制**：面板与存储都在 desktop 子树内，因此它们的行为由该子树自身的测试与打包后的应用验证，而不在 harness 的逐文件覆盖率门禁之内。

## 测试

`desktop/packages/plugin-store/tests/` 覆盖 manifest 校验（必填字段、不支持的服务器类型、路径逃逸、`user_config` 拒绝、平台覆盖）、归档安全（穿越型条目名、非归档文件、缺失 manifest、解压替换）、存储端到端（安装、跨进程边界真实调用一次工具、停用、启用、卸载、无法启动的插件、缺少入口的包），以及基于真实 HTTP 的路由面。

其中一个用例安装的是真正的外部包：把 `@modelcontextprotocol/server-everything` 连同其解析出的依赖闭包打包成 bundle 后安装，走的正是已发布第三方包所走的同一条路径。执行该打包的 `desktop/packages/plugin-store/tests/support/bundles.ts` 包含了包管理器布局所要求的符号链接解析。
